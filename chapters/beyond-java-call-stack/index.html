Before You Begin

Later chapters do not assume that you have read this one. Come here when bytecode, optimization, or native execution helps answer a question you care about.

+.1Three Kinds of Claim

Our first experiment will produce an impressive-looking bytecode listing. Before it does, we need a rule that keeps impressive output from becoming folklore.

  1. Language guarantee: the Java Language Specification requires it.
  2. Virtual-machine guarantee: every conforming JVM must provide it.
  3. Implementation observation: we saw it in one compiler, JVM, operating system, or processor.

Keep asking, “Which layer promised this?” It is a small question with an excellent record of preventing nonsense.

+.2Trace an Operand Stack

The expression x + y looks atomic in source. The JVM still needs to fetch two values, combine them, and keep the result somewhere. Start with the smallest useful method:

Download BytecodeDemo.java 
public final class BytecodeDemo {
    static int adjust(int x, int y) {
        int sum = x + y;
        return sum * 2;
    }
}

A typical javac compilation uses local slots for x, y, and sum. Bytecode instructions move values between those slots and the frame's operand stack.

Do not overclaim. The bytecode trace describes required JVM semantics. It does not provide a stop-motion film of physical memory after the JVM optimizes the method.

10-Minute Investigation: Look Under the Source

Predict the local slots and operand-stack contents. Then compile the example with debugging metadata and inspect its bytecode:

javac -g BytecodeDemo.java
javap -c -l -p BytecodeDemo

Explain which observations come from Java, which come from the JVM specification, and which belong only to this compiler run.
